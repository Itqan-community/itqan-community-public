# PHP2Shell — CVE-2026-109618 / CVE-2026-109619

**Status:** repo-side hardening and deploy gate implemented on branch
`security/php2shell-hardening`. No production change, no deploy, no push.
**Date:** 2026-10-21 · **Fixed release:** 2026-10-21 14:00 UTC (scheduled).

## Why this is urgent

Two remote-code-execution flaws in PHP core, both CVSS v4.0 **9.2**, with no
user interaction and no application bug required: any PHP request that reaches
the runtime is a potential entry point. Cloudflare reported early exploitation
attempts before the patch shipped and deployed WAF rules for all plans,
including free. PHP core developers say the only real mitigation is patching
PHP; the widely shared `session.upload_progress.enabled=0` line lowers exposure
but is not a fix.

PHP ships fixes for **8.2, 8.3, 8.4 and 8.5 only**. **8.1 and older are
end-of-life and will never get an official patch.**

## Exposure as it stands

| Environment | Runtime | State |
|---|---|---|
| Production (`community.itqan.dev`) | Ubuntu 22.04, **PHP 8.1 FPM**, nginx | **No upstream fix exists for 8.1** — upgrade required |
| Staging (`staging.community.itqan.dev`) | Ubuntu 22.04, **PHP 8.1 FPM**, nginx | Same |
| Local Docker (`docker compose up`) | `php:8.3-apache` | Fixed by rebuilding after the release |
| `itqan-community-v2` (not deployed) | PHP 8.3 | Follow-up: same `php.ini` hardening when it ships |

`deploy-prod.yml` and `deploy-staging.yml` both reload `php8.1-fpm`; the app is
at `/var/www/flarum` behind nginx. There is no application-level fix for this:
Flarum is not the vulnerable component, PHP is.

What already helps:

- Both sites are behind Cloudflare, which has WAF rules for the known exploit
  vectors (a stopgap, not a fix).
- The production droplet's DigitalOcean firewall accepts 80/443 only from
  Cloudflare ranges (`infra/cloudflare-ips.txt`, checked by
  `scripts/check-cloudflare-ips.sh`), so the origin is not directly reachable
  by IP. Keep that true — a WAF in front of a reachable origin protects nobody.

## What this branch changes (local only)

1. `.docker/php.ini` — `session.upload_progress.enabled = Off`,
   `session.upload_progress.cleanup = On`, `session.use_strict_mode = 1`.
2. `docker-compose.yml` — `build.pull: true`, so a rebuild after the release
   actually fetches the patched `php:8.3-apache` instead of reusing 8.3.35.
3. `scripts/security/php-version-gate.sh` — fails closed when the runtime is
   below the fixed version, or on an EOL branch (8.1), with a documented
   `PHP2SHELL_ALLOW_VULNERABLE=1` emergency override.
4. `scripts/security/harden-php2shell.sh` — read-only report by default;
   `--apply` writes the two INI directives into every installed PHP branch and
   pins them per FPM pool with `php_admin_flag`, validates with `php-fpm -t`,
   and reloads the running FPM services.
5. `.github/workflows/deploy-{prod,staging}.yml` — the deploy now identifies
   the FPM runtime nginx actually talks to, runs the gate on it, and reloads
   whichever `php*-fpm` services are running instead of hard-coding 8.1.
6. `security/nginx/php2shell-block-multipart.conf` — emergency-only nginx
   snippet; not included anywhere by default because it breaks all uploads.

The gate is deliberately fail-closed: merging this into `main` will block the
next production deploy until the runtime is upgraded. That is the point. The
override exists for a genuine emergency, and it logs.

## Owner actions (live, each one gated by the golden rule)

### 1. Two-minute read-only check (safe)

```bash
# Use the community SSH recipe in knowledge/gotchas/community-ssh-and-db-access.md:
# hostnames and Linux users drift, so resolve them there instead of pasting an IP.
ssh <community-prod-host>
cd /var/www/flarum

# after this branch is merged:
bash scripts/security/harden-php2shell.sh
php-fpm8.1 -v
grep -R "fastcgi_pass" /etc/nginx/sites-enabled/
```

The script exits 1 and lists exactly which directives/pools are missing. It
never writes unless `--apply` is passed.

### 2. Interim hardening — today, before the patch is installed

Staging first, then production:

```bash
sudo bash scripts/security/harden-php2shell.sh --apply
```

This adds:

- `/etc/php/<v>/fpm/conf.d/99-php2shell.ini`
- `php_admin_flag[session.upload_progress.enabled] = off` and
  `php_admin_flag[session.use_strict_mode] = on` in every pool

It runs `php-fpm<v> -t` before reloading and does not reload a broken config.
Re-run without `--apply`: the directives should now read Off/On for every SAPI.
The script still exits 1 on this box because 8.1 is end-of-life — that exit code
is the version warning, not a missing setting.

Verify the value reached FPM, not just the files (a probe file is the only
honest check; delete it immediately):

```bash
sudo tee /var/www/flarum/public/php2shell-probe.php >/dev/null <<'PHP'
<?php
header('Content-Type: text/plain');
echo 'PHP ', PHP_VERSION, ' ', PHP_SAPI, "\n";
echo 'session.upload_progress.enabled=', ini_get('session.upload_progress.enabled'), "\n";
echo 'session.use_strict_mode=', ini_get('session.use_strict_mode'), "\n";
PHP
curl -s https://community.itqan.dev/php2shell-probe.php
sudo rm /var/www/flarum/public/php2shell-probe.php
```

Expect `PHP 8.1… fpm-fcgi`, `enabled=`, `use_strict_mode=1`. `enabled` off
prints as empty/`0` depending on the getter; what matters is that it is not
`1`. If it is `1`, the pool is overriding the file — the script's
`php_admin_flag` lines are what stops that.

### 3. The fix: move production and staging to patched PHP 8.3

PHP 8.1 will never be patched. Upgrading is not optional, and the Docker dev
environment already runs Flarum 1.8 on 8.3, so application compatibility is
already exercised.

```bash
# On the server, with 8.1 left installed for rollback.
sudo add-apt-repository -y ppa:ondrej/php
sudo apt-get update
sudo apt-get install -y php8.3-fpm php8.3-cli php8.3-common \
  php8.3-mysql php8.3-curl php8.3-mbstring php8.3-xml php8.3-zip \
  php8.3-gd php8.3-intl php8.3-bcmath php8.3-opcache

# Match the Flarum limits the old pool had (256M, 20M uploads).
sudo tee /etc/php/8.3/fpm/conf.d/99-flarum.ini >/dev/null <<'INI'
memory_limit = 256M
upload_max_filesize = 20M
post_max_size = 24M
display_errors = Off
display_startup_errors = Off
log_errors = On
error_reporting = E_ALL & ~E_DEPRECATED & ~E_STRICT
INI

# Point nginx at the 8.3 socket. Keep a copy for rollback.
sudo cp /etc/nginx/sites-available/flarum.conf /root/flarum.conf.pre-php83
sudo sed -i 's#/run/php/php8.1-fpm.sock#/run/php/php8.3-fpm.sock#' \
  /etc/nginx/sites-available/flarum.conf
sudo nginx -t && sudo systemctl reload nginx
sudo systemctl enable --now php8.3-fpm

# CLI and the queue worker must use the same branch as FPM.
sudo update-alternatives --set php /usr/bin/php8.3
sudo -u www-data php -v
sudo -u www-data php -m | grep -E '^(curl|exif|gd|intl|mbstring|pdo_mysql|xml|zip)$'
sudo -u www-data php flarum cache:clear

# Reload/restart the queue worker if one exists.
systemctl list-units --type=service | grep -i flarum || true
```

Then re-run the gate; it must pass before the next deploy:

```bash
bash scripts/security/php-version-gate.sh --fpm "$(command -v php-fpm8.3)"
```

Confirm the fixed version published at 14:00 UTC is what is installed. The
fixed patch levels are recorded in `security/php2shell-fixed-versions.txt`
(confirmed 2026-10-21: 8.2.35, 8.3.36, 8.4.27, 8.5.12).

### 4. If the fix cannot land today

In order of preference:

1. **Keep the origin behind Cloudflare only** and confirm the WAF rules are on.
   An origin reachable by IP bypasses every WAF rule.
2. **Emergency multipart block** — copy
   `security/nginx/php2shell-block-multipart.conf` to
   `/etc/nginx/snippets/`, include it in the Flarum `server {}` block, then
   `nginx -t && systemctl reload nginx`. This **breaks all uploads** (post
   images, avatars, banners). Declare it, and remove it the moment PHP is
   patched.
3. **Take PHP off the internet.** Flarum's own `offline` flag is not enough:
   PHP parses the request before Flarum runs. Use nginx to serve a static 503,
   or stop FPM:

   ```bash
   sudo systemctl stop php8.1-fpm     # full outage, instant
   ```

   Use `scripts/maintenance-mode.sh` only for the UI banner; it is not a
   security control here.

### 5. After patching

- Re-run the gate and the FPM probe; both must be clean.
- Exercise login, posting, image upload, avatar upload, admin extension page,
  and preview cards. Uploads are the path the interim INI settings touch.
- Review access logs for multipart requests to unexpected paths and for
  requests that returned 200 before the patch; keep them somewhere safe.
- Rotate any secret that lived on the box if there is any sign of a web shell
  (new files under `public/`, `storage/`, unusual `www-data` processes).
- Remove the interim drop-in only after the runtime is on a fixed release; the
  settings are safe to keep, but they should not be mistaken for the fix.

## Rollback

- nginx socket: restore `/root/flarum.conf.pre-php83`, `nginx -t`,
  `systemctl reload nginx`.
- Interim INI: delete `/etc/php/<v>/fpm/conf.d/99-php2shell.ini`, remove the
  `php_admin_flag[...]` lines the script appended, `php-fpm<v> -t`, reload.
- None of this touches application data or the database.

## Deliberate non-actions

- No production/staging change, no SSH, no deploy, no push from this branch.
- The multipart block is not enabled by default; it would break the forum's
  core upload flows.
- `itqan-community-v2` gets the same `php.ini` treatment as a follow-up, since
  it is not deployed yet.
